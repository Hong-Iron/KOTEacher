# KOTEacher 구조와 구현

> KOTEacher는 프로그래머스 문제 90개로 코딩 테스트를 연습하는 데스크톱 앱입니다. 학생이 코드를 실행하면 앱이 예시 입력과 숨은 검사(문제 화면에 보이지 않는 채점용 입력과 답)로 채점합니다. 틀렸으면 코치(틀린 줄을 짚고, 그 줄의 값을 직접 따라가 보게 하는 질문 하나를 건네는 기능)가 말풍선을 띄웁니다. 이 문서는 이 일을 하는 프로세스 셋, 채점 방법, 틀린 줄을 찾는 방법, 코치 말에서 정답이 새지 않게 막는 방법, 기록과 설치를 코드 이름과 함께 설명합니다.

## 읽는 법

- 독자는 파이썬 코드를 읽을 줄 알고, 이 앱은 처음 보는 사람입니다.
- 앞에서부터 읽으면 '한 장 구조 → 실행 한 번 → 채점 → 문제 자료 → 코치 → 기록 → 설치 → 품질 재기' 순서입니다. 특정 파일을 찾을 때는 맨 끝의 [코드 지도](#파일별-줄-수와-하는-일)를 봅니다.
- 시간 제한과 개수는 코드의 상수에서 읽었고, 파일과 상수 이름을 함께 적었습니다. 정확도와 응답 시간은 `eval/results/`의 측정 파일에서 읽었고, MacBook Air M3(메모리 16GB)에서 잰 값입니다.
- 그림은 [`docs/architecture/diagrams.py`](architecture/diagrams.py)가 만듭니다. 그림을 고친 뒤에는 저장소 맨 위에서 `python3 docs/architecture/diagrams.py`를 실행합니다. 표준 라이브러리만 씁니다.
- 긴 예시와 상수 설명은 접어 두었습니다.

## 한 장으로 보는 구조: 한 컴퓨터에서 도는 프로세스 셋

![KOTEacher 한 장 구조](architecture/01-overview.svg)

KOTEacher에는 서버가 없습니다. 학생 컴퓨터 한 대에서 프로세스 셋이 돕니다.

| 프로세스 | 하는 일 | 코드 |
|---|---|---|
| 앱 프로세스 | 창을 띄우고, 화면이 부르는 함수를 실행하고, 기록을 SQLite 파일에 씁니다 | `koteacher/app.py`, `koteacher/api.py` |
| 검사 프로세스 | 학생 코드를 실행해 채점합니다. 실행할 때마다 새로 띄우고, 결과를 내면 끝납니다 | `koteacher/harness.py` |
| Ollama 서버 | 내 컴퓨터에서 언어 모델을 돌리고, HTTP로 부르게 해 주는 프로그램입니다. 코치 모델을 돌립니다. 학생이 외부 API를 고르면 이 자리를 OpenAI·Anthropic 같은 회사 서버가 대신합니다 | 외부 프로그램, 부르는 쪽은 `koteacher/ollama.py`·`remote.py` |

앱 프로세스 안은 두 층입니다. 창은 WebView(운영체제가 주는, 앱 창 안에 웹 페이지를 그리는 부품)가 그립니다. 맥에서는 WKWebView, 윈도에서는 WebView2입니다. 화면은 HTML·CSS·JS로 짰고(`ui/`), 화면 뒤의 일은 파이썬이 합니다(`koteacher/`).

**학생 코드를 따로 띄운 프로세스에서 돌리는 이유.** 학생 코드는 무한 루프를 돌거나, 재귀가 너무 깊어 파이썬을 죽이거나, 메모리를 다 쓸 수 있습니다. 이런 코드를 앱 프로세스에서 돌리면 창까지 멈춥니다. 따로 띄운 프로세스는 죽어도 괜찮습니다. 앱은 "검사 프로세스가 결과 없이 끝났습니다"를 보여 주고 계속 돕니다(`runner.check`).

검사 프로세스는 파이썬을 `-I` 옵션으로 띄웁니다. `-I`는 격리 모드(PYTHON으로 시작하는 환경 변수와 사용자 패키지 폴더를 무시하고, 스크립트 폴더를 import 경로에 넣지 않는 실행 방식)입니다. 그래서 학생 코드가 앱의 파일을 import하지 못합니다. PyInstaller(파이썬 앱을 파이썬 없이 열리는 실행 파일로 묶는 도구)로 묶은 앱에는 `python` 실행 파일이 따로 없으므로, 앱 자신을 `--harness` 인자로 한 번 더 띄웁니다(`config.child_cmd`). 이 인자는 묶은 앱의 시작 파일 `koteacher_main.py`가 받아 검사를 돌립니다.

## 화면과 파이썬이 서로 부르는 방법

화면과 파이썬은 pywebview(파이썬에서 WebView 창을 띄우고, 화면의 JS와 파이썬 함수가 서로 부르게 해 주는 라이브러리)로 이어져 있습니다. 방향마다 방법이 다릅니다.

**화면 → 파이썬: 함수 부르기.** 화면은 `window.pywebview.api.check(code, "run")`처럼 `Api` 객체(`koteacher/api.py`)의 메서드를 부릅니다. 반환값은 JSON으로 바뀌어 JS의 Promise로 돌아옵니다. `Api`의 공개 메서드 50개가 화면이 부를 수 있는 함수 목록입니다. 창을 만들 때 `webview.create_window(..., js_api=api)`로 이 객체를 넘깁니다(`koteacher/app.py`).

**파이썬 → 화면: 이벤트 보내기.** 코치 말이나 모델 받기처럼 몇 초 넘게 걸리는 일은 파이썬이 따로 스레드를 띄워 합니다. 끝나거나 진행이 있으면 이벤트(파이썬이 화면에 보내는 알림. 이름 하나와 JSON 자료 하나로 되어 있습니다)를 보냅니다. `Api._push(event, data)`가 `window.evaluate_js("KG.on(이름, 자료)")`를 부르고, 화면의 `KG.on`(`ui/app.js`)이 이름에 따라 나눠 처리합니다.

| 이벤트 | 보내는 때 | 화면이 하는 일 |
|---|---|---|
| `thinking` | 코치가 모델을 부르기 시작할 때 | '코치가 생각하고 있습니다'를 띄웁니다 |
| `line` | 모델이 줄 번호를 먼저 써 보냈을 때 | 말풍선을 처음부터 그 줄 아래에 놓습니다 |
| `stream` | 모델이 글자 조각을 내보낼 때마다 | 말풍선에 이어 씁니다 |
| `diag` | AI 진단이 끝났을 때 | 진단 분류와 줄을 바꿉니다 |
| `say` | 코치 말이 정해졌을 때 | 말풍선을 확정하고 코치 기록 탭에 더합니다 |
| `chip` | 먼저 말하지 않기로 정했을 때 | 누르면 펼쳐지는 작은 표시를 띄웁니다 |
| `answer` | 학생이 직접 물은 질문의 답이 끝났을 때 | 그 질문의 상자에 답을 씁니다 |
| `coach_error` | 코치가 실패했을 때 | 실패를 알립니다. 테스트 결과는 그대로 둡니다 |
| `prep`, `pull`, `pull_done`, `model_ready` | 처음 실행의 준비, 모델 받기 | 진행 막대와 받는 속도를 그립니다 |
| `doc_stream`, `doc_answer` | 개념 문서에서 고른 부분을 물었을 때 | 문서 옆 답 상자에 씁니다 |
| `mistake_named` | 오답에 이름이 붙었을 때 | 오답 노트를 고칩니다 |

이벤트는 늦게 도착할 수 있습니다. 그래서 코치 이벤트에는 번호 두 개가 붙습니다.

<details><summary>gen(검사 번호)과 rid(질문 번호)의 뜻, 쓰는 곳, 빼면 생기는 일</summary>

**gen(검사를 시작할 때마다 1씩 오르는 번호).**

- 뜻: 늦게 도착한 코치 말이 지금 화면의 코드에 대한 말인지 확인하는 번호입니다.
- 코드에서 쓰는 곳: `Session.gen`(`api.py`). `check()`와 `exam_run()`이 락(여러 스레드가 같은 값을 동시에 바꾸지 못하게 막는 장치) 안에서 1 올립니다. 뒤 스레드가 보내는 `thinking`·`line`·`stream`·`diag`·`chip`·`say` 이벤트에 붙습니다. `_current(s, gen)`은 `gen == s.gen`일 때만 참이고, 거짓이면 이벤트를 보내지 않습니다.
- 빼면 생기는 일: 1번 실행(gen=1)의 AI 진단에 8초가 걸리는 사이 학생이 코드를 고쳐 다시 실행하면(gen=2), 1번 실행의 말이 늦게 도착해 이미 고친 줄을 짚습니다. 지금은 gen=1 말을 버립니다.
- 값의 출처: 문제를 열 때 만든 `Session`이 0에서 시작합니다. '처음부터'를 누를 때도 새 `Session`이 생깁니다.

**rid(학생이 코치에게 직접 물을 때마다 화면이 만드는 번호).**

- 뜻: 답을 어느 질문 상자에 쓸지 정하는 번호입니다. 모양은 `q<밀리초 시각>-<순번>`입니다(`app.js`).
- 코드에서 쓰는 곳: `ask(question, code, sel, rid, thread)`가 받아 `stream`·`answer` 이벤트에 붙입니다. 직접 물은 답은 `_current(s, None)`으로 확인하므로, 답을 기다리는 사이 검사가 다시 돌아도 버리지 않습니다.
- 빼면 생기는 일: 묻기의 답을 gen으로 거르면, 답을 기다리는 동안 자동 검사가 한 번만 돌아도 답이 버려집니다. 그러면 '코치가 생각하고 있습니다'가 끝나지 않습니다.
- 값의 출처: 화면이 질문 상자를 만들 때 정합니다.

</details>

## 실행 버튼을 누르면 일어나는 일

![실행 버튼을 누르면 일어나는 일](architecture/02-check-flow.svg)

그림의 번호를 따라 설명합니다.

1. 학생이 실행(⌘↵)을 누르거나, 편집을 멈춘 지 2.7초가 지나면 화면이 `check(code, trigger)`를 부릅니다. `trigger`는 누른 경우 `"run"`, 저절로 돈 경우 `"idle"`입니다. 자동 검사는 코드가 마지막 검사 때와 다를 때만 돕니다(`app.js`의 `runCheck`). 조용히 모드에서는 자동 검사를 하지 않습니다.
2. `Api.check`가 gen을 1 올리고, `runner.check`가 검사 프로세스를 띄워 코드와 팩(한 문제의 예시 입력·답과 숨은 검사 입력·답을 담은 JSON 파일) 경로를 표준 입력으로 넘깁니다.
3. 검사 프로세스가 결과 JSON을 표준 출력의 마지막 줄에 씁니다. 학생 코드가 찍은 `print`는 그 앞줄들에 섞여 나오므로, `{`로 시작하는 마지막 줄만 읽습니다.
4. `Api`가 실패 사실을 고릅니다(`coach.facts`). 실패 사실은 어느 검사에서, 어떤 입력으로, 어떻게 틀렸는지입니다. 틀린 답을 낸 입력을 반례(내 코드가 틀린 답을 내는 입력)라고 부릅니다. 수리 검색(코드의 연산자나 숫자를 한 군데씩 바꿔 보며, 모든 검사를 통과하게 되는 수정을 찾는 과정)이 수정을 찾았으면 진단까지 여기서 합니다. 테스트 결과는 여기서 바로 화면에 돌아갑니다. 버그 하나를 심은 코드 258개에서 검사와 수리 검색을 합친 시간의 가운데값은 76 ms였습니다(`eval/results/det.json`).
5. 수리 검색이 수정을 못 찾았으면, 뒤 스레드(`Api._coach_bg`)가 코치 모델에게 진단을 맡깁니다. 모델이 쓰는 글자는 `stream` 이벤트로 바로 흘려 보냅니다.
6. 정책(코치가 먼저 말할지, 접어 둘지 정하는 규칙 묶음)이 먼저 말할지 정하고(`coach.Policy`), `say` 또는 `chip` 이벤트를 보냅니다.

몇 가지 경우는 이 흐름을 줄여 끝냅니다.

- 모든 검사를 통과했을 때: 시도(문제를 한 번 연 때부터 다시 열 때까지 남는 풀이 기록 한 줄)를 통과로 적고, 앞서 못 고친 실패가 있었으면 오답 기록을 남기고 끝납니다.
- 문법 오류나 불러오기 오류일 때: 그 줄에 작은 표시만 하고 모델을 부르지 않습니다.
- `solution` 함수 본문의 문장이 2개 이하일 때(`coach.is_stub`): 아직 풀이가 없다고 보고 코치가 기다립니다.
- 수리 검색으로 확인한 진단이고 정책이 '말한다'로 정했을 때: 정해진 문장(모델 없이 줄 번호와 반례만 채워 넣는 문장 틀)을 바로 띄우고, 모델이 쓴 질문이 준비되면 그 자리를 바꿉니다.

## 학생 코드를 채점하는 검사 프로세스

`koteacher/harness.py`는 `koteacher` 패키지를 import하지 않는 파일 하나입니다. 표준 입력으로 `{"code", "pack", "repair", "only"}`를 받아 아래 순서로 검사합니다.

1. **문법.** `ast.parse`가 실패하면 줄·칸·메시지만 내고 끝납니다.
2. **불러오기.** 코드를 `exec`로 실행해 `solution` 함수를 꺼냅니다. 함수가 없거나 함수 밖 코드에서 오류가 나면, 그 오류와 줄 번호를 내고 끝납니다.
3. **예시.** 팩의 예시를 차례로 돌립니다.
4. **숨은 검사.** 입력이 짧은 순서로 돌리다가 처음 틀린 입력에서 멈춥니다. 그 입력을 학생에게 반례로 보여 줍니다.
5. **실행 추적과 수리 검색.** 실패가 있을 때만 합니다. 실행 추적은 반례를 넣고 돌리며, 줄마다 바뀐 지역 변수 값을 적은 표입니다.

답을 비교할 때는 튜플과 리스트를 같게 보고, 실수는 소수점 아래 9자리로 반올림해 비교합니다(`norm`). 튜플과 리스트를 같게 보는 규칙은 프로그래머스 채점에 맞췄습니다(`norm` 주석).

### 시간 제한 규칙

| 규칙 | 코드 |
|---|---|
| 테스트 하나가 2초를 넘으면 시간 초과로 적고, 남은 테스트를 돌리지 않습니다. 무한 루프라면 남은 테스트도 오래 걸리기 때문입니다. | `PER_TEST = 2.0` |
| 예시에서 시간 초과가 났으면 숨은 검사를 돌리지 않습니다. | `main()` |
| 숨은 검사를 시작한 지 3초가 지나면 남은 숨은 검사를 돌리지 않습니다. 이때는 다 돌지 못했으므로 통과로 치지 않습니다. | `HIDDEN_BUDGET = 3.0`, `coach.passed` |
| 실전 모드의 제출은 틀린 입력이 나와도 끝까지 돌립니다. 다만 12초가 지나거나 시간 초과가 2번 나면 멈춥니다. 입력이 짧은 순서라 남은 입력은 더 크기 때문입니다. | `SUBMIT_BUDGET = 12.0` |
| 검사 프로세스 전체가 20초 안에 끝나지 않으면 앱이 프로세스를 끊고 "검사가 20초 안에 끝나지 않았습니다"를 보여 줍니다. | `runner.check(timeout=20)` |
| 학생 코드의 `print` 출력은 앞에서 4,000자까지만 보여 줍니다. | `MAX_OUT = 4000` |

<details><summary>시간 제한을 거는 방법과 그 한계</summary>

**무엇이 보이나.** `while True: pass`를 실행하면 2초 뒤 '시간 초과'가 뜨고, 앱은 그대로 돕니다.

**보통의 온라인 채점기에서는.** 테스트마다 프로세스를 띄우고 운영체제에 CPU 시간 한도를 걸어, 넘으면 운영체제가 프로세스를 죽입니다.

**우리 코드에서는.** `Deadline(2.0)`이 `threading.Timer`로 2초 뒤에 `_thread.interrupt_main()`을 부릅니다. 이 함수는 주 스레드에 `KeyboardInterrupt`를 던집니다. `call()`이 이 예외를 잡아 `{"timeout": True}`를 적습니다. `KeyboardInterrupt`는 `Exception`의 자식이 아니므로, 학생 코드의 `except Exception:`에 잡히지 않습니다. 이 방법은 맥·리눅스·윈도에서 똑같이 돕니다(`Deadline` 주석). 흔히 쓰는 `signal.alarm`은 윈도에 없습니다.

**왜 다른가.** 테스트 340개를 한 프로세스에서 이어 돌리므로, 테스트마다 프로세스를 띄우는 비용이 없습니다. 대신 두 가지를 놓칩니다.

- 파이썬은 바이트코드 명령 사이에서만 이 예외를 확인합니다. 그래서 C로 짠 함수 하나가 오래 돌면(예: 아주 큰 리스트의 `sorted`) 그 함수가 끝날 때까지 끊지 못합니다.
- 학생 코드에 맨 `except:`나 `except BaseException:`이 있으면 예외를 삼키고 계속 돌 수 있습니다.

두 경우 모두 `runner.check`의 20초 제한이 프로세스를 끊습니다. 학생은 테스트 표 대신 "검사가 20초 안에 끝나지 않았습니다"를 봅니다.

**어떻게 고치나.** 아직 하지 않았습니다. 맥·리눅스에서는 `resource.setrlimit`로 CPU 시간 한도를 걸면 C 함수 안에서도 끊을 수 있습니다. 윈도에는 이 함수가 없어서, 윈도는 지금 방법을 그대로 써야 합니다.

</details>

<details><summary>PER_TEST·HIDDEN_BUDGET의 뜻, 바꾸면 달라지는 점, 값의 출처</summary>

- **PER_TEST(테스트 입력 하나에 주는 시간, 초).** `harness.call(fn, args, limit)`의 `limit`로 쓰입니다. 1초로 줄이면 파이썬으로 짠 O(n log n) 정답 풀이도 큰 입력에서 시간 초과로 떨어질 수 있습니다. 5초로 늘리면 무한 루프 코드가 결과를 보이기까지 5초씩 기다려야 합니다. 코드 주석에는 2초를 고른 근거가 적혀 있지 않습니다.
- **HIDDEN_BUDGET(숨은 검사 전체에 주는 시간, 초).** `run_tests(..., budget=HIDDEN_BUDGET)`가 테스트를 하나 돌릴 때마다 지난 시간을 보고, 3초를 넘었으면 멈춥니다. 늘리면 느린 풀이도 끝까지 채점하지만, 학생이 손을 멈출 때마다 도는 자동 검사가 그만큼 오래 걸립니다. 코드 주석에는 3초를 고른 근거가 적혀 있지 않습니다.

</details>

### 실행 추적: 반례에서 줄마다 바뀐 변수

실패한 입력 가운데 `repr` 길이가 가장 짧은 입력을 고릅니다. 그 길이가 300자 이하일 때만 실행 추적을 만듭니다. `trace_run`이 `sys.settrace`로 줄 이벤트를 받아, 줄 하나를 실행한 뒤 값이 바뀐 변수만 적습니다. 40줄까지, 0.5초까지 적고, 변수 값의 `repr`은 40자에서 자릅니다. 코치 모델에게는 `L5 i=0 total=1`처럼 줄여서 앞 16줄을 넘깁니다(`coach.trace_text`). `L5`는 '5번 줄을 실행한 뒤'라는 뜻입니다.

### 수리 검색: 한 군데만 바꿔 모든 검사를 통과하는지

**무엇이 보이나.** 코치가 "확인됨"이라는 표시와 함께 줄 하나를 바로 짚습니다. 모델을 부르지 않으므로 0.1초 안팎에 나옵니다.

**사람 조교라면.** 경계 조건 실수는 한 글자 차이가 많습니다(`<` 대신 `<=`, `n` 대신 `n - 1`). 조교는 의심 가는 곳을 하나씩 바꿔 돌려 봅니다.

**우리 코드에서는.** `harness.repair(code, failing, all_tests)`가 같은 일을 기계로 합니다.

1. `mutation_sites(tree)`가 코드의 문법 트리(코드를 문장과 식 단위로 쪼개 나무 모양으로 늘어놓은 자료)를 훑어 바꿔 볼 자리를 모읍니다. 바꾸는 방법은 아래 표의 일곱 가지입니다.
2. 자리마다 `apply_mutation`으로 한 군데만 바꾼 코드를 만듭니다.
3. 바꾼 코드로 실패한 입력부터 돌립니다. 실패한 입력은 최대 3개이고, 시간 초과가 있었으면 2개입니다. 입력 하나에 0.2초(`REPAIR_PER_TEST`)를 줍니다.
4. 실패한 입력을 모두 통과하면 예시와 숨은 검사 앞 120개를 0.6초 안에 돌립니다. 이 검사도 통과하면 수정 하나로 적습니다(줄, 바꾼 내용, 실수 분류).
5. 1.5초(`REPAIR_BUDGET`)가 지나거나, 바꾼 코드 400개를 돌렸거나, 수정을 3개 찾으면 멈춥니다.

| 바꾸는 방법 | 예 | 실수 분류 |
|---|---|---|
| 비교 연산자 바꾸기 | `<` ↔ `<=`, `>` ↔ `>=`, `==` ↔ `!=` | 비교·경계 |
| 정수 상수 ±1 (인덱스 안의 상수는 빼고) | `0` → `1`, `0` → `-1` | 비교·경계 |
| `and` ↔ `or` | `a and b` → `a or b` | 조건 놓침 |
| `+` ↔ `-` | `i + 1` → `i - 1` | 기타 |
| `min` ↔ `max` | `min(a, b)` → `max(a, b)` | 기타 |
| `range` 인자 ±1 (상수가 아닌 인자만) | `range(n - 1)` → `range(n - 1 + 1)` | 인덱스 |
| 인덱스 ±1 (슬라이스와 상수 인덱스는 빼고) | `a[i]` → `a[i + 1]` | 인덱스 |

**왜 사람 조교와 다른가.** 한 군데만 바꾸므로, 버그가 두 군데이면 수정을 찾지 못합니다. 그때는 코치 모델이 진단합니다. 또 찾은 수정이 검사는 통과해도 학생이 뜻한 고침과 다를 수 있습니다. 그래서 코치는 수정 내용을 학생에게 말하지 않고, 줄만 짚어 질문합니다.

**어떻게 고치나.** 두 군데를 함께 바꾸는 조합은 아직 찾지 않습니다. 자리가 k곳이면 조합이 k² 가까이로 늘어 1.5초 안에 다 돌기 어렵습니다.

<details><summary>수리 검색의 줄 적중률: 버그 하나를 심은 코드 258개에서 95.7%</summary>

**무엇을 셌나.** `eval/data/bugs1.json`의 258개입니다. `eval/bugs.py`가 문제마다 모범 풀이를 꺼내, 위 표의 일곱 가지 방법 가운데 하나로 한 군데를 바꿉니다. 바꾼 코드가 실제로 검사에서 떨어질 때만 남깁니다. 바뀐 줄이 정답 줄입니다.

**점수 규칙.** 코치가 첫 진단에서 짚은 줄이 바뀐 줄이면 1점, 아니면 0점입니다. 모델은 부르지 않습니다(`eval/run_eval.py det`).

**계산.**

- 수리 검색이 수정을 찾은 코드: 243개 ÷ 258개 = 94.2%. 그중 짚은 줄이 맞은 코드: 236개 ÷ 243개 = 97.1%
- 오류나 시간 초과로 규칙 단계가 짚은 코드: 11개, 모두 맞음
- 어느 단계도 줄을 못 짚어 모델이 필요한 코드: 4개
- 합계: (236 + 11) ÷ 258 = 95.7%
- 검사와 수리 검색을 합친 시간: 가운데값 76 ms, 가장 오래 걸린 코드 5.9초

**뜻.** 버그를 심은 방법과 수리 검색이 바꿔 보는 방법이 같은 일곱 가지입니다. 그래서 이 점수는 '찾을 수 있는 버그를 시간 안에 찾는가'를 잽니다. 학생의 실제 실수는 이 일곱 가지 밖에 있을 수 있으므로, 실제 학생 코드에서는 이 점수보다 낮게 나올 수 있습니다. 실제 학생 코드로 잰 값은 아직 없습니다.

**근거.** `eval/results/det.json`(코드마다 단계, 짚은 줄, 버그 줄, 걸린 시간).

</details>

## 코치가 틀린 줄을 찾는 방법

![코치가 틀린 곳을 찾고 말하는 과정](architecture/03-coach-pipeline.svg)

### 실패 사실 고르기

`coach.facts(result)`가 검사 결과에서 실패를 모아 가르칠 순서로 줄 세웁니다. 오류(예외)가 오답보다, 오답이 시간 초과보다 앞입니다. 종류가 같으면 입력이 짧은 실패가 앞입니다. 코치는 맨 앞의 실패 하나만 다룹니다.

### 확실한 단계부터 쓰는 세 단계 진단

`coach.diagnose`는 확실한 방법부터 씁니다.

| 단계 | 쓰는 때 | 짚는 줄 | 표시 |
|---|---|---|---|
| 규칙 | 문법 오류나 불러오기 오류일 때 | 오류가 난 줄 | 확인됨 |
| 수리 검색 | 한 군데 수정으로 모든 검사를 통과할 때 | 첫 수정의 줄 | 확인됨 |
| AI 진단 | 그 밖의 경우 | 모델이 고른 줄 | 추정 |

AI 진단이 실패하면(모델이 꺼져 있거나 답이 비었으면) 규칙 단계로 돌아갑니다. 오류라면 오류가 난 줄을 짚고, 오답이라면 줄 없이 반례만 보여 줍니다.

실수 분류는 아홉 가지입니다: 비교·경계, 초기값, 인덱스, 자료구조, 복잡도, 조건 놓침, 빈 입력, 예외, 기타. 시간 초과인데 모델이 이 넷(복잡도, 조건 놓침, 비교·경계, 초기값) 밖의 분류를 고르면 복잡도로 바꿉니다.

<details><summary>AI 진단의 방법: 모델에게 무엇을 주고 무엇을 받나</summary>

**무엇이 보이나.** 수리 검색이 수정을 못 찾으면 몇 초 뒤 말풍선이 줄 아래에 뜨고, 질문이 한 글자씩 흘러나옵니다.

**사람 조교라면.** 반례를 손으로 넣어 따라가며, 변수 값이 처음 기대와 어긋나는 줄을 찾습니다. 오류가 난 줄과 원인 줄이 다른 경우가 많으므로, 오류가 난 줄을 그대로 짚지 않습니다.

**우리 코드에서는.** `coach.diagnose_and_say`가 대화 메시지 네 개를 만들어 모델에게 보냅니다(`coach.messages`).

1. 지시문(모델에게 역할과 규칙을 알려 주는 첫 메시지): 정답 코드나 바꿀 값을 말하지 않는다, 증거에 없는 버그를 지어내지 않는다, 반례에서 그 줄의 값을 따라가 보게 하는 질문을 두 문장 100자 안으로 쓴다
2. 사용자 메시지: 문제 앞 420자와 줄 번호를 붙인 학생 코드
3. 모델의 답 자리에 미리 넣은 "문제와 코드를 읽었습니다."
4. 사용자 메시지: 증거와 할 일. 증거는 실패한 곳·입력·기대한 답·내 답, 실행 추적 16줄, 학생이 연 힌트, 이 학생이 자주 틀리는 분류 3개, 코치가 이미 한 말 2개입니다. 할 일은 아래 세 줄로만 답하라는 요청입니다.

```text
줄: 6
말: 6번 줄에서 i가 마지막 값일 때 arr[i + 1]은 어디를 가리킬까요? 반례 [3]으로 한번 따라가 보세요.
분류: 인덱스
```

모델이 쓰는 답의 길이는 `max_tokens=120`으로 묶어 둡니다. `TextStream`이 흘러오는 글자에서 `줄:` 값을 읽자마자 `line` 이벤트를 보내므로, 말풍선이 처음부터 그 줄 아래에 뜹니다. 이어지는 `말:` 글자는 `stream` 이벤트로 보냅니다. 다 받으면 `parse_text`가 세 줄을 읽고, 줄 번호가 1에서 코드 줄 수 사이가 아니면 버립니다. 말은 유출 검사(코치 말에 정답 코드나 고칠 값이 들어 있는지 찾는 검사)를 거칩니다. 자세한 규칙은 아래 [정답이 새지 않게 막는 방법](#코치-말에서-정답이-새지-않게-막는-방법)에 있습니다.

JSON 형식으로 받지 않고 이름표를 붙인 글로 받는 이유는 속도입니다. JSON의 괄호·따옴표와 원인 칸을 쓰지 않아, 응답이 약 13% 빨리 끝났습니다(`coach.py`의 `diagnose_and_say` 주석).

**왜 사람 조교와 다른가.** 모델은 실행 추적을 끝까지 따라가지 않고 그럴듯한 줄을 고르기도 합니다. 버그를 두 군데 심은 12문제에서 기본 모델이 버그 줄을 맞힌 문제는 9개입니다(아래 [모델마다 다른 프로필](#모델마다-다른-프로필과-그-성적)).

**어떻게 고치나.** 아직 하지 않았습니다. 실행 추적에서 값이 처음 기대와 달라지는 줄 후보를 코드로 먼저 좁히고, 모델은 그 후보 가운데서 고르게 하는 방법이 있습니다.

</details>

### 첫 응답을 빠르게 하는 앞부분 재사용

모델에게 보내는 메시지 전체를 프롬프트라고 부릅니다. 모델은 프롬프트를 처음 읽을 때 초당 약 100토큰(모델이 글을 잘라 읽고 쓰는 단위. 낱말 조각 하나쯤입니다)을 읽습니다(M3 16GB, `coach.py`의 `SYSTEM` 위 주석). 대신 Ollama는 앞부분이 같은 프롬프트의 계산 결과를 다시 씁니다. 이 기능을 앞부분 재사용이라고 부릅니다. 같은 주석에는 재사용될 때 읽는 시간이 10초에서 1초 안팎으로 줄었다고 적혀 있습니다.

그래서 모든 호출이 '지시문 → 문제와 코드 → 미리 넣은 답' 세 메시지로 똑같이 시작하고, 매번 바뀌는 증거는 맨 뒤 메시지에 둡니다. 문제를 열면 `coach.warm`이 앞 두 메시지만 보내고 1토큰만 받아, 모델이 앞부분을 미리 계산해 두게 합니다. 외부 API를 쓸 때는 요청 한 번이 요금이므로 `warm`을 보내지 않습니다.

## 코치가 먼저 말할지 정하는 규칙

학생은 코치가 얼마나 먼저 나설지 조용히, 보통, 적극 세 모드 가운데 고릅니다. 코드에서는 `quiet`, `normal`, `active`입니다. `Policy.decide(mode, trigger, diag)`는 아래 규칙을 위에서부터 보고, 처음 맞는 규칙을 따릅니다.

1. 진단이 없을 때는 아무 표시도 하지 않습니다.
2. 실패가 문법 오류일 때는 칩(코치 말을 바로 띄우지 않고, 누르면 펼쳐지는 작은 표시)만 띄웁니다.
3. 조용히 모드일 때는 칩만 띄웁니다.
4. 같은 실수 분류, 같은 줄, 같은 반례 입력으로 이미 말했을 때는 칩만 띄웁니다.
5. 자동 검사이고, 마지막으로 자동 검사에서 말한 지 180초가 안 됐을 때는 칩만 띄웁니다.
6. 자동 검사이고, 보통 모드이고, 진단이 '확인됨'이 아닐 때는 칩만 띄웁니다.
7. 그 밖에는 말합니다.

규칙 5와 6 때문에, 학생이 실행을 누르지 않는 동안 코치는 많아야 3분에 한 번, 보통 모드에서는 수리 검색으로 확인한 실수만 먼저 말합니다. 실행을 누르면 규칙 2~4에 걸리지 않는 한 늘 말합니다.

<details><summary>AUTO_GAP(180초)의 뜻, 바꾸면 달라지는 점, 값의 출처</summary>

- **뜻.** 자동 검사에서 코치가 먼저 말한 뒤, 다음 자동 검사에서 다시 먼저 말하기까지 기다리는 시간(초)입니다.
- **코드에서 쓰는 곳.** `Policy.AUTO_GAP`, `Policy.last_auto`. `Policy.spoke`가 자동 검사에서 말할 때마다 `last_auto`를 지금 시각으로 바꿉니다.
- **바꾸면 달라지는 점.** 60으로 줄이면, 손을 멈출 때마다(2.7초) 도는 자동 검사에서 1분에 한 번씩 말풍선이 뜰 수 있습니다. 0으로 하면 규칙 4(같은 말은 다시 하지 않음)만 남습니다.
- **값의 출처.** 코드 주석에는 값을 고른 근거가 적혀 있지 않습니다.

</details>

## 코치 말에서 정답이 새지 않게 막는 방법

**무엇이 보이나.** 코치는 고칠 코드를 말하지 않고 질문만 합니다. 모델이 정답을 말해 버리면, 학생은 모델 말 대신 정해진 문장을 봅니다.

**사람 조교라면.** 답을 알아도 "이 줄에서 i가 마지막 값일 때 무엇을 가리킬까요?"처럼 묻습니다. 고칠 곳을 알려 주면 학생이 스스로 찾는 연습을 건너뛰기 때문입니다.

**우리 코드에서는.** 모델 말을 보여 주기 전에 `coach.leak_reason(msg, diag, pid)`가 정규식과 문자열 비교로 유출 검사를 합니다. 아래 가운데 하나라도 걸리면 그 이유를 돌려줍니다.

| 걸리는 조건 | 예 | 코드 |
|---|---|---|
| 말이 비었을 때 | | |
| 말이 320자를 넘을 때 | | |
| 코드처럼 생긴 줄이 있을 때: ` ``` `, 줄 머리의 `def`·`for`·`while`·`if`·`return` 문, `이름[...] =` 대입 | "for i in range(n):를 보세요" | `CODEY` |
| 'A 대신 B'에서 B가 기호(`[ ] ( ) = < > + - * / %`)를 품은 20자 이하 영문·숫자일 때 | "j 대신 j + 1을 써 보세요" | `REPLACE_WITH` |
| 물음표로 끝나지 않는 문장에 '바꿔야 합니다', '고쳐야 해요', '쓰면 됩니다' 같은 말이 있을 때 | "8번 줄의 초기값을 바꿔야 할 것 같습니다." | `FIX_TOLD` |
| 모범 풀이의 줄(공백을 정리한 뒤 18자 이상인 줄)이 말 안에 그대로 있을 때 | | `_reference_lines` |
| 수리 검색이 찾은 고칠 값 바로 뒤에 '로 바꾸', '를 써', '사용', '넣'이 올 때 | "<=로 바꾸면 돼요" | `leak_reason` |

걸린 뒤의 처리는 진단 단계에 따라 다릅니다.

- 수리 검색으로 확인한 진단은 말을 따로 한 번 더 받습니다(`coach.say`). 걸리면 "규칙 위반(코드가 들어 있음). 고치는 법을 빼고 질문으로 다시 써라."를 덧붙여 한 번 더 쓰게 합니다. 또 걸리면 정해진 문장을 씁니다.
- AI 진단은 진단과 말을 한 번에 받으므로, 걸리면 바로 정해진 문장을 씁니다.

정해진 문장(`coach.template`)은 실패 종류와 실수 분류로 고릅니다. 예: "입력 [1, 2]의 기대 답은 3, 내 답은 2예요. 6번 줄의 비교가 같은 값일 때 어떻게 되는지 따라가 보세요."

**왜 사람 조교와 다른가.** 정규식은 글자 모양만 봅니다. "등호를 하나 더 붙여 보세요"처럼 기호 없이 말로 바꿔 쓴 유출은 잡지 못합니다. 걸린 개수는 셉니다. 'A 대신 B'와 '~바꿔야 합니다' 검사는 기본 모델의 코치 말 44개에서 하나도 걸지 않았고, Ministral 3 8B의 말에서는 고칠 곳을 대놓고 말한 5개를 잡았습니다(`eval/results/compare.md`). 놓친 유출의 개수는 아직 재지 않았습니다.

**어떻게 고치나.** 아직 하지 않았습니다. 사람이 코치 말에 '유출'·'아님' 표시를 붙인 시험 자료를 만들면, 정규식이 놓치는 비율을 잴 수 있습니다. 모델을 한 번 더 불러 판정하게 하는 방법도 있지만, 응답 시간이 그만큼 늘어납니다.

## 모델마다 다른 프로필과 그 성적

지시문은 기본 모델(gemma4 e4b)의 답을 읽으며 다듬었습니다. 다른 모델은 버릇이 달라서, 같은 지시문을 주면 줄 번호 이름표를 빼먹거나, 질문 대신 원인을 단정하거나, 굵은 글씨를 섞습니다. 모델에게 주는 값 가운데 온도(모델이 다음 토큰을 고를 때 얼마나 무작위로 고를지 정하는 값)도 모델마다 알맞은 값이 다릅니다. 그래서 모델 계열마다 프로필(지시문·온도·대화 구조·말 다듬기를 한데 묶은 설정)을 따로 둡니다(`coach.PROFILES`).

| 프로필 | 고르는 때 | 지시문 | 온도 (진단 / 말 / 묻기) | 대화 구조 | 말 다듬기 |
|---|---|---|---|---|---|
| `gemma` | 아래 둘에 걸리지 않을 때 (기본) | 한국어, 짧게 | 0.3 / 0.5 / 0.4 | 나눔 | 없음 |
| `mistral` | 모델 이름에 `mistral`이 있을 때 | 앱과 코치의 자리를 먼저 밝히고, 질문 하나·80자 안을 못 박음 | 0.05 / 0.05 / 0.05 | 나눔 | 굵은 글씨·따옴표를 지우고 첫 질문 뒤를 자름 |
| `qwen` | 모델 이름에 `qwen`이나 `omnicoder`가 있을 때 | 답 예시 하나로 형식을 못 박음 | 0.7 / 0.7 / 0.7 | 한 덩어리 | 없음 |

`profile_name()`은 외부 API를 쓰면 그 API의 모델 이름, 아니면 Ollama 모델 이름으로 고릅니다. 환경 변수 `KOTEACHER_PROMPT`를 주면 이름과 상관없이 그 프로필을 씁니다. 비교할 때만 쓰는 영어 지시문 프로필(`en`, `qwen_en`)도 같은 표에 있습니다.

<details><summary>온도와 대화 구조의 뜻, 바꾸면 달라지는 점, 값의 출처</summary>

**온도.**

- 코드에서 쓰는 곳: `ollama.chat(..., temperature=pr["temp_diag"])`. 진단(`temp_diag`), 확인된 진단의 말(`temp_say`), 학생이 직접 물은 답(`temp_ask`)에 따로 씁니다.
- 바꾸면 달라지는 점: 0에 가까우면 같은 입력에 거의 같은 답을 냅니다. 높이면 말이 다양해지지만 형식(`줄:` 이름표)을 어기는 일이 늘어납니다. Qwen은 온도가 낮으면 같은 말을 되풀이하기 쉬워 0.7을 씁니다(`coach.py`의 `QWEN_SYSTEM` 위 주석).
- 값의 출처: `mistral`의 0.05는 Ministral 3 8B 모델 카드의 권장(0.1 아래)을 따랐습니다. `qwen`의 0.7은 Qwen 권장값입니다(같은 주석). `gemma`의 0.3·0.5는 근거가 코드에 적혀 있지 않습니다.

**대화 구조(`split`).**

- 뜻: '나눔'은 문제·코드와 증거·할 일을 두 사용자 메시지로 나누고, 그 사이에 미리 넣은 모델 답을 둡니다. '한 덩어리'는 사용자 메시지 하나에 다 넣습니다.
- 코드에서 쓰는 곳: `coach.messages`. 나눔일 때만 앞부분 재사용이 됩니다.
- 바꾸면 달라지는 점: 한 덩어리로 보내면 매번 바뀌는 증거가 앞 메시지에 섞여, 앞부분 재사용이 되지 않습니다. 그만큼 첫 응답이 느려집니다.
- 값의 출처: `coach.py`의 `QWEN_SYSTEM` 위 주석에 적혀 있습니다. Qwen 3.5의 버릇(이름표를 빼고 답함, 질문 대신 원인을 단정함, '14 번 줄'처럼 띄어 씀)을 줄이려고, 지시문을 예시 하나로 못 박으면서 미리 넣은 모델 답 없이 한 덩어리로 보냅니다.

</details>

<details><summary>기본 모델과 Ministral 3 8B의 성적: 버그 줄 적중 9/12와 7/12</summary>

**무엇을 셌나.** `eval/data/_sub/bugs2.json`의 12문제입니다. 모범 풀이에 버그를 두 군데 심은 코드라서, 한 군데만 바꾸는 수리 검색으로는 고칠 수 없고 AI 진단으로 갑니다. 버그를 두 군데 심은 81문제(`eval/data/bugs2.json`) 가운데, 앞선 측정에서 모델이 줄을 놓친 문제 전부(7개)와 맞힌 문제 5개를 골랐습니다(`eval/subset.py`). 그래서 81문제 전체보다 어려운 묶음입니다.

**점수 규칙.**

- 줄 적중: 모델이 고른 줄이 버그를 심은 두 줄 가운데 하나이면 1점입니다.
- 응답 끝: 진단을 요청한 때부터 학생이 볼 말을 다 받은 때까지의 시간(초)입니다. 12문제의 가운데값을 씁니다.
- 첫 글자: 학생이 볼 말의 첫 글자가 도착하기까지의 시간입니다.
- 질문으로 끝남: 모델이 쓴 말(정해진 문장으로 바뀐 말은 빼고) 가운데 물음표로 끝나는 말의 수입니다.
- 유출: 평가 코드가 따로 판정한 유출 수입니다. 위 12문제의 말과, 버그 하나를 심은 10문제의 말을 합친 22개에서 셉니다.

**계산.**

| 모델 · 프로필 | 줄 적중 | 응답 끝 가운데값 | 첫 글자 | 질문으로 끝남 | 유출 (22개 중) | 말 길이 가운데값 |
|---|---|---|---|---|---|---|
| `ghcr.io/hong-iron/gemma4-e4b-text` · `gemma` | 9 ÷ 12 = 75.0% | 4.6초 | 3.2초 | 17 / 21 | 0 | 51자 |
| `Ministral-3-8B-Instruct-2512` Q4_K_M · `mistral` | 7 ÷ 12 = 58.3% | 14.2초 | 9.1초 | 19 / 21 | 0 | 55자 |

**뜻.**

- 한 문제가 8.3%포인트이므로, 두 모델의 차이는 두 문제입니다. 12문제로는 '기본 모델이 줄을 더 잘 맞힌다'를 단정할 수 없습니다. 반면 응답 시간은 12문제 모두에서 Ministral이 2.5~3.4배 느렸습니다(`total` 칸).
- 줄 적중은 줄만 봅니다. 말이 학생에게 도움이 되는지는 재지 않습니다.
- 두 모델 모두 말 22개 가운데 1개를 앱의 유출 검사가 정해진 문장으로 바꿨습니다(빈 답도 이 검사에 걸립니다). 그래서 '질문으로 끝남'의 분모가 21이고, 평가 코드가 본 말에는 유출이 남지 않았습니다.
- 그래서 기본 모델은 e4b로 두고, Ministral은 설정에서 고를 수 있는 선택지로 둡니다. Ministral은 반례 값을 넣어 구체적으로 묻는 장점이 있습니다.

<details><summary>Ollama</summary>

**무엇인가.** 내 컴퓨터에서 언어 모델을 돌리는 프로그램입니다. 모델 파일을 받아 두고, `127.0.0.1:11434`에서 `/api/chat`, `/api/pull` 같은 HTTP 요청을 받습니다. MIT 라이선스입니다.

**우리 코드에서 하는 일.** `ollama.chat`이 `/api/chat`에 메시지와 온도, 생성할 최대 토큰 수를 보내고, 흘러오는 답을 한 줄씩 읽어 `on_token`으로 넘깁니다. 문맥 길이는 8,192토큰(`config.NUM_CTX`)이고, 모델을 30분 동안 메모리에 두게 합니다(`keep_alive: "30m"`). 앱을 켤 때 모델을 미리 올리고, 앱이 올린 모델이었을 때만 끌 때 내립니다.

**좋은 점.** 학생 코드가 컴퓨터 밖으로 나가지 않고, 요금이 없습니다. 앞부분 재사용으로 같은 문제의 두 번째 응답부터 빨라집니다.

**문제.** 모델이 메모리 5~7GB를 차지합니다. 메모리 16GB 맥에서 다른 큰 앱과 함께 쓰면 느려집니다. 첫 실행 때 5GB 넘게 받아야 합니다.

**보완.** 메모리가 모자라면 외부 API를 고를 수 있습니다. 검사와 수리 검색은 모델 없이 돌기 때문에, 모델이 없어도 문제 풀기와 반례 보기는 됩니다.

</details>

<details><summary>gemma4 e4b 글 전용판 (ghcr.io/hong-iron/gemma4-e4b-text)</summary>

**무엇인가.** 모델의 가중치를 적은 비트로 줄여 저장하는 방법을 양자화라고 부릅니다. `gemma4:e4b-it-qat`은 Google이 gemma4 e4b를 QAT(양자화로 잃을 정밀도를 미리 감안해 학습시키는 방법)로 만든 판입니다. 이 판에서 그림을 읽는 부분(약 1GB)만 뺀 모델이 글 전용판이고, 크기는 5.2GB입니다. Ollama가 보여 주는 라이선스는 Apache 2.0입니다(`ollama show <모델> --license`).

**우리 코드에서 하는 일.** 기본 코치 모델입니다(`config.CHOICES["fast"]`). `tools/push_ghcr.py`로 개발자 계정의 GitHub 패키지(`ghcr.io/hong-iron`)에 올려 두었고, `ollama pull ghcr.io/hong-iron/gemma4-e4b-text`로 받습니다.

**좋은 점.** 코치는 글만 주고받으므로 답은 원래 모델과 같고, 받을 양만 약 1GB 줄어듭니다. 같은 12문제에서 12B보다 응답이 약 2배 빠르고, 버그 줄 적중은 9/12로 12B(6/12)보다 낮지 않았습니다(`README.md`, `ollama.recommend`의 주석).

**문제.** GitHub 패키지에서 받다가 끊기는 일이 있습니다. 공식 Ollama 저장소의 판이 아니므로, 원래 모델이 고쳐져도 저절로 따라 바뀌지 않습니다.

**보완.** 끊기면 받던 데서 이어 3번까지 다시 받고, 그래도 안 되면 Ollama 저장소의 `gemma4:e4b-it-qat`를 받습니다([설치와 처음 실행](#설치와-처음-실행) 참고). 이미 `gemma4:e4b-it-qat`가 있으면 그 모델을 씁니다.

</details>

<details><summary>Ministral 3 8B (hf.co/mistralai/Ministral-3-8B-Instruct-2512-GGUF:Q4_K_M)</summary>

**무엇인가.** Mistral AI가 만든 지시 모델의 가중치를 4비트로 줄인 GGUF 파일(llama.cpp와 Ollama가 읽는 모델 파일 형식)입니다. Hugging Face(모델 파일을 올려 두고 받는 사이트)의 `mistralai` 계정에서 받으며 6.1GB입니다. 모델 정보를 옮긴 여러 사이트는 Apache 2.0으로 적습니다. Ollama가 보여 주는 정보에는 라이선스가 없습니다[확인 필요: 공식 모델 카드의 라이선스 칸].

**우리 코드에서 하는 일.** 설정의 'Ministral 3 8B'를 고르면 이 모델을 받고(`config.MINISTRAL`), 이름에 `mistral`이 있으므로 `mistral` 프로필이 저절로 골립니다.

**좋은 점.** 반례 값을 넣어 구체적으로 묻습니다. 맞춤 프로필에서는 21개 말 가운데 19개가 질문으로 끝났습니다.

**문제.** 같은 12문제에서 버그 줄 적중이 7/12로 기본 모델보다 낮고, 응답이 약 3배 느립니다(14.2초). 질문표 없이 원인을 단정하거나, 문자열을 숫자라고 하는 식의 틀린 전제를 깔기도 합니다.

**보완.** `mistral` 프로필의 말 다듬기(`polish_mistral`)가 첫 질문 뒤의 설명을 자릅니다. 고칠 곳을 대놓고 말하면 유출 검사가 정해진 문장으로 바꿉니다. 기본 모델로 두지 않습니다.

</details>

<details><summary>gemma4 12B와 외부 API</summary>

**gemma4 12B (`gemma4:12b-it-qat`).**

- 무엇인가: Google의 gemma4 12B를 QAT로 만든 판입니다. 7.2GB입니다.
- 우리 코드에서 하는 일: 설정에서 '정확도 우선'을 고르면 받습니다(`config.CHOICES["accurate"]`).
- 좋은 점: e4b보다 큰 모델입니다.
- 문제: 같은 12문제에서 버그 줄 적중이 6/12로 e4b(9/12)보다 높지 않았고, 응답은 약 9초로 e4b(약 5초)보다 느렸습니다(`README.md`).
- 보완: 자동 선택은 e4b입니다(`ollama.recommend`). 12B는 학생이 고를 때만 씁니다.

**외부 API.**

- 무엇인가: 회사 서버에서 도는 언어 모델을 HTTP로 부르는 서비스입니다. OpenAI, Anthropic, Google Gemini, OpenRouter, Groq와 OpenAI 형식을 따르는 서버를 고를 수 있습니다(`config.PROVIDERS`). 요청마다 요금이 듭니다.
- 우리 코드에서 하는 일: `remote.chat`이 OpenAI 형식(`/chat/completions`)이나 Anthropic 형식(`/messages`)으로 보냅니다. 설정 화면에서 키를 시험하고(`Api.api_test`) 모델 목록을 받습니다(`Api.api_models`). 키는 앱 데이터 폴더의 `settings.json`에 저장하고, 파일을 내 계정만 읽게 권한을 바꿉니다(`config.save_settings`).
- 좋은 점: 메모리가 적은 컴퓨터에서도 코치를 쓰고, 더 큰 모델을 쓸 수 있습니다.
- 문제: 문제와 학생 코드가 회사 서버로 갑니다. 프로필은 모델 이름으로 고르므로, GPT나 Claude 같은 모델에는 `gemma` 프로필이 골립니다. 이 조합의 성적은 재지 않았습니다. 요청 한 번이 요금이라 앞부분 재사용을 위한 `warm`도 보내지 않습니다.
- 보완: 기본은 Ollama이고, 외부 API는 학생이 설정에서 고를 때만 씁니다.

</details>

<details><summary>pywebview, Monaco, KaTeX와 Mermaid, pyflakes</summary>

- **pywebview.** 파이썬에서 WebView 창을 띄우고, JS가 파이썬 객체의 메서드를 부르게 하고, 파이썬이 `evaluate_js`로 JS를 실행하게 해 주는 라이브러리입니다(BSD 라이선스). 좋은 점은 Electron처럼 브라우저 엔진을 앱에 넣지 않아 앱이 가볍다는 점입니다. 문제는 맥과 윈도의 WebView 엔진이 달라서, 한쪽에서만 생기는 화면 버그가 있을 수 있다는 점입니다. 윈도에서는 WebView2 런타임이 있어야 합니다. 보완할 일은 윈도 실제 기기에서 화면을 시험하는 일이고, 아직 하지 않았습니다.
- **Monaco.** VS Code에 쓰이는 코드 편집 부품입니다(MIT). 좋은 점은 학생이 실제 시험 환경과 비슷한 편집기를 쓴다는 점입니다. 문제는 크기입니다. 화면 라이브러리를 모아 둔 `ui/vendor/` 9.1MB 가운데 6.0MB가 Monaco입니다. 쓰지 않는 언어 지원을 빼면 줄일 수 있지만, 아직 하지 않았습니다.
- **KaTeX와 Mermaid.** 수식과 흐름도를 화면에서 그리는 JS 라이브러리입니다(둘 다 MIT). `koteacher/render.py`가 문서의 `$…$` 수식과 ` ```mermaid ` 블록을 그대로 남겨 두면, 화면에서 이 둘이 그립니다. 좋은 점은 공부 노트와 같은 문법을 그대로 쓴다는 점입니다. 문제는 크기로, `ui/vendor/`에서 Mermaid가 2.5MB, KaTeX가 0.6MB입니다. 인터넷 없이 화면이 떠야 하므로 이 크기를 그대로 둡니다.
- **pyflakes.** 코드를 실행하지 않고 읽기만 해서 안 쓴 변수, 정의하지 않은 이름을 찾는 검사기입니다(MIT). 앱 프로세스에서 돌려도 안전하므로, 학생이 타이핑하는 동안 밑줄을 긋는 데 씁니다(`koteacher/lint.py`). 실행해야 알 수 있는 실수는 찾지 못하므로, 그 몫은 검사 프로세스가 합니다.

</details>

<details><summary>PyInstaller, Inno Setup, GitHub 패키지, GitHub Actions</summary>

- **PyInstaller.** 파이썬 앱과 필요한 모듈을 묶어, 파이썬을 설치하지 않은 컴퓨터에서도 열리는 실행 파일로 만드는 도구입니다(GPL 2.0에 예외 조항이 붙어, 묶은 앱은 다른 라이선스로 배포할 수 있습니다). 우리 코드에서는 `tools/build_mac.py`와 `tools/build_win.py`가 씁니다. 학생 코드가 import할 표준 모듈(`heapq`, `bisect`, `collections` 등)을 직접 적어 함께 묶습니다(`STDLIB_FOR_USERS`). 문제는 묶을 때 빠진 모듈을 학생 코드가 import하면 그 자리에서 오류가 난다는 점입니다. 그래서 묶은 앱에 `--harness`로 `heapq`·`collections`를 import하는 시험 코드를 넣어, 검사가 도는지 확인한 뒤에만 DMG를 만듭니다.
- **Inno Setup.** 윈도 설치 파일(`Setup.exe`)을 만드는 도구입니다. 설정은 `tools/KOTEacher.iss`에 있습니다. 관리자 권한 없이 내 계정의 `%LOCALAPPDATA%\Programs\KOTEacher`에 설치하고, 시작 메뉴와 (고르면) 바탕 화면에 아이콘을 만듭니다. 문제는 설치 파일에 코드 서명을 하지 않아, 윈도가 '알 수 없는 게시자' 경고를 띄울 수 있다는 점입니다. 서명 인증서를 사는 일은 아직 하지 않았고, 같은 릴리스의 zip은 설치 없이 풀어서 쓸 수 있습니다.
- **GitHub 패키지(ghcr.io).** 공개 패키지는 계정 없이 받을 수 있고, Ollama는 `ollama pull ghcr.io/…`로 여기서 모델을 받습니다. 올리는 쪽은 `tools/push_ghcr.py`가 모델 덩어리를 조각으로 나눠 올리고, 끊기면 서버가 알려 주는 위치부터 이어 올립니다. 처음 올린 패키지는 비공개이므로, GitHub의 패키지 설정에서 공개로 바꿔야 학생이 받을 수 있습니다.
- **GitHub Actions.** `v`로 시작하는 태그를 올리면 GitHub의 윈도 서버에서 `build_win.py`를 돌리고, 만든 `Setup.exe`와 zip을 그 태그의 릴리스에 붙입니다(`.github/workflows/build.yml`). 좋은 점은 윈도 컴퓨터 없이 윈도 앱을 만든다는 점입니다. `build_win.py`는 묶은 실행 파일에 `--harness`와 `--run`을 넣어 검사와 개념 코드 실행이 도는지까지 확인합니다. 문제는 창을 띄워 화면을 써 보지는 않는다는 점입니다. 보완은 윈도 실제 기기 시험이고, 아직 하지 않았습니다.

</details>

## 기록: SQLite 표와 통과 규칙

기록은 앱 데이터 폴더의 `koteacher.db` 파일 하나에 있습니다(`koteacher/store.py`). 표는 다섯 개입니다.

| 표 | 한 줄이 뜻하는 일 | 주요 칸 | 쓰는 화면 |
|---|---|---|---|
| `attempts` | 문제를 한 번 연 때부터의 시도 | 모드, 시작·끝 시각, 결과, 연 힌트 수, 풀이 봄 | 홈의 문제 상태, 추천, 풀이 기록 |
| `snapshots` | 실행 한 번 | 그때 코드, 결과 요약, 통과 여부 | 다시 열 때 이어 쓸 코드, 프로필의 날짜별 칸 |
| `coach_msgs` | 코치가 한 말 한 번 | 진단 단계, 줄, 걸린 시간, 학생이 준 평가 | 풀이 기록의 코치 말 |
| `mistakes` | 틀렸다가 고친 일 한 번 | 실수 분류, 고치기 전후 코드와 차이, 고치는 데 걸린 시간, 학생 메모 | 오답 노트, 약한 분류의 문제 추천 |
| `doc_notes` | 개념 문서에서 고른 부분을 물은 질문 하나 | 고른 글, 질문, 답, 이어서 물은 질문과 답 | 문서의 하이라이트, 전체 검색 |

![통과가 기록되는 규칙](architecture/05-status.svg)

**통과 규칙.** 시도의 결과와 받은 도움으로 정합니다(`store.problem_status`).

- 모든 검사를 통과한 시도에서 연 힌트가 2개 이상이거나 풀이를 봤을 때, 그 시도는 '힌트로 통과'입니다. 힌트가 1개 이하일 때는 '통과'입니다.
- 힌트는 3단계까지 있고, 그다음 단계가 '풀이 보기'입니다(`vault.HINTS = 3`). 코치 말에 붙은 예제 코드의 알고리즘 틀을 펼친 횟수도 힌트로 셉니다(`Session.extra_hints`).
- 문제 상태는 그 문제의 시도 가운데 가장 좋은 결과입니다. 통과한 시도가 하나라도 있으면 '통과'입니다.
- 실전 모드에서, 그 시도에서 연습 검사를 한 번도 돌리지 않고 힌트 0개로 제출해 통과했을 때만 '실전 통과'입니다(`store.exam_passes`).

**도움을 이어 받는 규칙.** 지난 시도의 코드를 이어 쓰면, 그 시도에서 연 힌트 수와 '풀이 봄'도 새 시도에 함께 적습니다(`Api._carry`). 이어 쓰는 경우는 문제를 다시 열 때 마지막 코드를 불러올 때, 풀이 기록에서 '이 코드 불러오기'를 누를 때, '처음부터'를 누를 때입니다. 홈 추천의 '다시 풀기'만 빈 기록으로 엽니다. 이 규칙이 없으면, 힌트로 푼 코드를 다시 열기만 해도 자동 검사가 그 코드를 돌려 힌트 0개인 새 시도가 통과합니다. 그러면 문제 상태가 '통과'로 바뀝니다.

**오답 기록 규칙.** 진단이 생기면 그 실패를 '아직 못 고친 실패'로 들고 있습니다(`Session.open_fail`). 그 뒤 통과하면 고친 차이와 걸린 시간을 `mistakes`에 적습니다. 고치기 전에 풀이를 보면 '못 고침'으로 적습니다. 코치는 `mistakes`에서 가장 많이 나온 실수 분류 3개를 증거에 넣어, 그 학생이 자주 틀리는 쪽을 먼저 의심하게 합니다(`store.weak_categories`).

**프로필 규칙.** 날짜별 칸은 그날 코드를 실행한 문제 수로 칠합니다. 0개면 빈 칸, 1개, 2개, 3~4개, 5개 이상이 차례로 진한 색입니다(`app.js`의 `heatLv`). '처음부터'를 누를 때 저장한 코드와 실전 모드의 시간 끝 표시는 실행이 아니므로 세지 않습니다(`store.RUN`). 날짜는 내 컴퓨터의 시각으로 나눕니다.

## 실전 모드: 도움 없이 제한 시간 안에 풀기

실전 모드(`Api.set_exam`)는 실제 코딩 테스트처럼 풉니다.

- 자동 검사, 코치, 힌트, 반례 보기를 끕니다. 예시 실행과 제출만 남습니다(`Api.exam_run`).
- 예시 실행은 예시만 돌립니다. 제출은 숨은 검사를 끝까지 돌려 통과 개수만 보여 줍니다. 반례, 실행 추적, 수리 검색은 돌리지 않습니다.
- 학생이 정한 제한 시간(분)이 끝난 뒤에도 계속 풀면(`Api.exam_overtime`), 그 뒤의 통과는 실전 통과로 치지 않습니다.
- 그 시도에서 연습 모드의 검사를 한 번이라도 돌렸으면, 통과해도 실전 통과가 아닙니다(`Session.practiced`).

## 설치와 처음 실행

![앱을 만드는 과정과 처음 켤 때 코치를 준비하는 과정](architecture/06-build-setup.svg)

**맥 앱 만들기.** `tools/build_mac.py`가 팩 90개를 만들고, PyInstaller로 `.app`을 묶고, 임시 서명(`codesign --sign -`)을 하고, 묶은 앱에 `--harness`로 시험 코드를 넣어 검사가 도는지 확인한 뒤, DMG를 만듭니다. Apple 공증(Apple 서버가 앱을 검사하고 통과 표시를 붙이는 절차)을 받지 않았으므로, 다른 맥에서 DMG로 받은 앱을 열면 "손상되었기 때문에 열 수 없습니다"가 뜹니다. 파일은 망가지지 않았습니다. 인터넷에서 받은 파일에 붙는 표시 때문에 뜹니다. README가 그 표시를 지우는 명령(`xattr -dr com.apple.quarantine /Applications/KOTEacher.app`)을 안내합니다. 빌드는 Apple 실리콘 맥에서만 했으므로 DMG는 arm64용입니다.

**한 줄 설치.** `install.sh`(맥, 리눅스)와 `install.ps1`(윈도)은 파이썬을 확인하고, 저장소를 받아 가상 환경과 패키지를 설치하고, 팩을 만들고, Ollama와 코치 모델을 받고, 앱 아이콘을 만듭니다. `curl`로 받은 파일에는 인터넷에서 받았다는 표시가 붙지 않으므로, 이 방법으로 설치하면 맥 경고가 뜨지 않습니다. 인텔 맥과 리눅스는 이 방법을 씁니다.

**처음 실행에서 코치를 준비하는 규칙(`Api.prepare_coach`).**

1. 외부 API를 고른 상태일 때는 준비할 일이 없습니다.
2. Ollama 서버가 켜져 있고 코치 모델도 있을 때는 그대로 씁니다.
3. 서버가 꺼져 있고 Ollama가 설치되어 있을 때는 Ollama를 켭니다. 30초 안에 켜지지 않으면 직접 실행하라고 안내합니다.
4. Ollama가 없을 때, 맥에서는 학생이 버튼을 누르면 `Ollama-darwin.zip`(약 221MB)을 받아 설치합니다. 윈도에서는 설치 방법을 안내합니다.
5. 서버가 켜졌는데 모델이 없을 때는 팝업을 띄우고 바로 기본 모델을 받기 시작합니다.

**모델 받기 규칙(`Api.pull_model`).**

- 한 번에 하나만 받습니다. 받는 중에 다시 부르면 무시합니다(`Api.pulling`).
- GitHub 패키지에서 받다가 실패하면 2초 × (시도 번호)만큼 기다린 뒤 다시 받습니다. Ollama는 받아 둔 조각을 이어 받으므로 처음부터 다시 받지 않습니다.
- 3번(`config.PULL_TRIES`) 실패하면 Ollama 저장소의 `gemma4:e4b-it-qat`를 받습니다(`config.FALLBACK`).
- 받는 동안 받은 양, 초당 MB, 남은 시간, 받는 곳을 보여 줍니다. Ollama는 모델 조각 여러 개를 함께 받으며 조각마다 진행을 따로 알려 줍니다. `ollama.Rate`가 조각별 받은 양을 더하고, 최근 8초 동안 늘어난 양으로 속도를 냅니다. 남은 시간은 (전체 크기 − 받은 양) ÷ 속도입니다. 예를 들어 최근 8초에 400MB가 늘었으면 초당 50MB이고, 2.6GB가 남았으면 남은 시간은 52초입니다.
- 팝업을 닫아도 받기는 계속되고, 화면 위 막대에 몇 %를 받았는지 보입니다.

## 코치 품질을 재는 방법

학생 코드를 모을 수 없으므로, 모범 풀이에 버그를 심어 '학생 코드'를 만들고 코치를 돌려 봅니다.

| 단계 | 하는 일 | 파일 |
|---|---|---|
| 시험 코드 만들기 | 모범 풀이에서 `solution`과 그 함수가 부르는 함수, import, 상수만 남깁니다. 수리 검색과 같은 일곱 가지 방법으로 한 군데 또는 두 군데를 바꾸고, 실제로 검사에서 떨어지는 코드만 남깁니다 | `eval/bugs.py` → `eval/data/bugs1.json`(258개), `bugs2.json`(81개) |
| 결정적 단계 재기 | 버그 하나를 심은 코드로 규칙과 수리 검색만 돌려 줄 적중과 시간을 잽니다 | `eval/run_eval.py det` |
| AI 진단 재기 | 버그 두 개를 심은 코드로 AI 진단과 말하기를 돌려 줄 적중, 시간, 말을 적습니다 | `eval/run_eval.py llm` |
| 말하기 재기 | 버그 하나를 심은 코드의 확인된 진단으로 말을 받아, 고칠 값을 흘리는지 봅니다 | `eval/run_eval.py say` |
| 모델 비교하기 | 모델마다 따로 프로세스를 띄워 위 두 가지를 돌리고, 한국어 품질(한자·가나 섞임, 영어 낱말 비율, 질문으로 끝나는지, 말 길이)을 세어 한 표로 모읍니다 | `eval/compare_models.py` → `eval/results/compare.md` |

평가하는 동안에는 앱을 꺼 둡니다. 앱이 다른 모델을 메모리에 붙잡고 있으면 메모리가 모자라 응답 시간이 틀어집니다. `compare_models.py`는 `compare.md`를 새로 쓰므로, 지난 표를 남기려면 `CMP_TAG`를 주고 표를 따로 붙입니다.

## 아직 해결하지 못한 문제

- **윈도·리눅스는 실제 기기에서 써 보지 않았습니다.** 윈도 앱은 GitHub Actions에서 만들어지는지만 확인합니다.
- **인텔 맥용 DMG가 없습니다.** 인텔 맥은 한 줄 설치를 써야 합니다.
- **DMG가 Apple 공증을 받지 않았습니다.** 그래서 '손상' 경고가 뜨고, 학생이 터미널 명령을 한 번 입력해야 합니다.
- **AI 진단의 버그 줄 적중이 12문제에서 9개(75%)입니다.** 12문제는 어려운 문제를 골라 모은 묶음이라 81문제 전체로 재면 달라질 수 있는데, 전체로는 아직 재지 않았습니다.
- **수리 검색의 95.7%는 낙관적인 값입니다.** 버그를 심은 방법과 찾는 방법이 같습니다. 실제 학생 코드로는 재지 않았습니다.
- **유출 검사가 정규식이라 말로 바꿔 쓴 유출을 놓칩니다.** 놓친 개수를 재지 않았습니다.
- **C 함수 안에서 오래 도는 코드는 2초에 끊지 못합니다.** 20초 뒤 검사 프로세스째 끊깁니다.
- **OmniCoder-9B는 `qwen` 프로필에 연결만 해 두었고, 성적을 재지 않았습니다.**
