설계 원칙

판정은 코드가, 말은 AI가

통과·실패·시간 초과는 실행 결과로만 정한다. 모델은 이미 확인된 사실을 사람 말로 옮긴다.

모르는 답은 새지 않는다

모델에게는 지금 힌트 단계까지의 풀이만 넘긴다. 아직 넘기지 않은 풀이는 모델도 모르니 흘릴 수가 없다.

타이핑 중에는 조용히

확실한 신호가 있을 때만 먼저 말한다. 나머지는 코치 창에 표시만 해 두고, 내가 열 때 보여 준다.

볼트는 읽기만

노트와 풀이 코드는 원본으로 둔다. 앱이 쓰는 곳은 review-log.csv에 한 줄 더하기와 앱 자체 DB뿐이다.

통과한 뒤가 진짜 연습

통과하면 내 말로 설명하고, 복잡도를 맞히고, 며칠 뒤 같은 문제를 다시 푼다.

문제

진열대에 보석이 한 줄로 놓여 있다. 모든 종류를 하나 이상 포함하는 가장 짧은 연속 구간을 [시작, 끝]으로 돌려준다. 번호는 1부터. 가장 짧은 구간이 여럿이면 시작 번호가 가장 작은 것.

필요한 개념 · 힌트 1단계에서 열림

원문은 프로그래머스 링크로 연다. 화면의 문제문은 볼트에 정리해 둔 요약이다.

1def solution(gems):
2 kinds = len(set(gems))
3 count = {}
4 left = 0
5 best = [1, len(gems)]
6 for right, g in enumerate(gems):
7 count[g] = count.get(g, 0) + 1
8 while count[gems[left]] > 1:
9 count[gems[left]] -= 1
10 left += 1
11 if len(count) == kinds and right - left <= best[1] - best[0]:
12 best = [left + 1, right + 1]
13 return best

개입 규칙

  • 타이핑하는 동안에는 아무것도 띄우지 않는다. 신호는 코치 창의 칩으로만 쌓인다.
  • 먼저 말하는 것은 3분에 한 번까지. 같은 신호로 두 번 말하지 않는다.
  • 한 번에 한 가지만 말한다. 세 문장을 넘기지 않는다.
  • 모델이 낸 확신 값이 낮으면 말하지 않고 칩만 남긴다.
  • 모드: 조용히는 내가 물을 때만, 보통은 테스트로 확인된 신호만, 적극은 방향 어긋남과 느릴 위험까지.

힌트 사다리

볼트의 풀이 문서가 이미 단계별로 접혀 있다. 그 단계가 그대로 힌트 단계가 된다. 모델에게 넘기는 자료도 단계마다 늘어난다.

단계내가 보는 것풀이 문서의 출처모델이 받는 자료
0 · 질문신호에 맞춘 질문 하나—문제 요약, 신호, 내 코드
1 · 개념필요한 개념 이름과 한 줄 설명「필요한 개념」 콜아웃+ 개념 문서 요약, 자주 하는 오해
2 · 작은 예손으로 푸는 작은 예, 단순한 방법이 왜 느린지1·2단계+ 1·2단계
3 · 핵심 아이디어핵심 아이디어와 떠올리는 신호3단계+ 3단계
4 · 코드 흐름번호 붙인 코드 흐름4단계+ 4단계
풀이 보기코드, 실행 추적, 흔한 실수5~7단계내가 직접 누를 때만. 기록에 "풀이 봄"

힌트를 2단계 이상 연 시도는 오답으로 기록한다. 지금 복습 카드에 쓰는 규칙과 같다. AI의 도움을 받으면 실력보다 많이 배웠다고 느끼기 쉽기 때문이다.

답이 새지 않게

  1. 정보 차단. 열리지 않은 단계의 풀이와 기준 풀이 코드는 프롬프트에 넣지 않는다. 기준 풀이는 실행 결과(기대값, 반례)로만 쓴다.
  2. 출력 형식 강제. Ollama의 JSON 스키마 출력으로 message를 220자 안으로 묶는다. 코드 블록 자리를 두지 않는다.
  3. 나중 검사. 코드처럼 보이는 줄이 2줄 넘거나, 기준 풀이와 겹치는 토큰 조각이 있으면 버리고 정해진 문장("11번 줄의 비교를 다시 보세요")으로 바꾼다.

코치 파이프라인

모델 하나에 큰 프롬프트를 한 번 보내지 않는다. 작은 단계를 여러 개 잇는다. 코드를 돌려서 알 수 있는 것은 전부 코드로 먼저 알아내고, 모델은 마지막에 짧게 두 번까지만 부른다.

  • 한 단계에 한 가지 일. 작은 모델은 "찾고, 판단하고, 말 고르기"를 한꺼번에 시키면 셋 다 흐려진다.
  • 진단과 말하기를 나눈다. 진단은 고치는 법까지 알아내지만, 말하기 단계에는 고치는 법을 넘기지 않는다. 모르는 답은 흘릴 수 없다.
  • 진단은 확실한 것부터. 알려진 실수와 출력이 같은지 보고, 한 글자 수정으로 고쳐지는지 찾는다. 둘 다 실패할 때만 모델이 추정한다.
  • 최신 코드만. 파이프라인이 도는 중에 내가 다시 타이핑하면 그 실행은 버리고 새로 시작한다.

④ 유출 검사코드말하기 결과, 숨겨 둔 고치는 법, 기준 풀이 코드통과 / 한 번 다시 / 분류별 정해진 문장10ms
⑤ 전달규칙모드, 마지막 발언 시각, 이미 말한 신호코치 창에 말하기, 또는 칩만—

모델 호출이 아무리 커도 4K 토큰을 넘지 않는다. 문맥 길이는 16K로 두면 넉넉하다.

시험해 본 결과

보석 쇼핑, 위 화면의 버그 코드, 결정적 단계만 (2026-10-21)

  • 예시 2/4 통과. 반례는 작은 크기부터 81개를 시도해 ["C","C"]를 찾았다 (기대 [1, 1], 내 답 [2, 2]).
  • 실수 지문: 미리 심어 둔 실수 두 개 중 "길이가 같을 때도 답을 바꿈"만 출력이 일치했다.
  • 수리 검색: 변이 25개를 0.01초에 돌려 11번 줄 <= → < 하나만 찾았다.
  • 실패한 방법: 실패한 실행에서 자주 지나간 줄을 의심하는 방법(SBFL)은 while문을 가리켰다. 반례가 되려면 같은 보석이 겹쳐야 해서 while문이 실패한 실행에서 더 자주 돌기 때문이다. 이 방법은 쓰지 않는다.
  • 전부 0.02초. 다만 한 문제, 한 버그로 해 본 것이다. 실제로는 별도 프로세스에서 돌리므로 더 걸린다. 알고리즘을 통째로 잘못 고른 경우는 한 글자 수정으로 못 고치니 AI 진단까지 간다.

@dataclass

@dataclass

다른 상황의 파이프라인

상황단계
아직 쓰는 중 (돌릴 코드가 없음)AST로 코드 요약 (함수, 반복문 깊이, 쓴 자료구조) → 복잡도 어림을 제한 크기와 비교 → AI가 접근을 개념 35개 중 하나로 분류 (JSON) → 이 문제의 필요 개념과 비교 → 다르면 적극 모드에서만 말하기
통과한 뒤입력 크기 4개(1천, 1만, 3만, 10만)로 시간을 재 로그-로그 기울기로 실제 복잡도를 구함 → 기준 풀이와 비교 → 내 설명을 핵심 요소별로 있음·없음 채점 → 돌아보기 요약
코치에게 묻기질문 분류 (개념 / 문제 이해 / 내 코드 / 답 달라는 요청) → 분류별로 재료 고르기, 답 요청이면 다음 힌트 단계를 제안 → 답하기 → 유출 검사

빌드 때 한 번 돌리는 파이프라인

실시간에 무거운 일을 하지 않으려고 문제마다 미리 만들어 둔다. 모두 코드로 검사하고 문제 팩에 넣는다.

  1. 문제 팩: 예시, 입력 생성기, 기준 풀이 (데이터 절 참고).
  2. 알려진 실수 변이체: 풀이 문서 7단계 「흔한 실수」 문장마다 기준 풀이를 그 실수대로 고친 코드를 하나씩 만든다. 기준 풀이와 다른 답을 실제로 내는지 확인하고, 같으면 버린다. 고정 입력 200개에 대한 출력이 그 실수의 지문이 된다.
  3. 핵심 요소 목록: 3단계 핵심 아이디어를 2~4개 요소로 나눈다. 설명 채점에 쓴다.
  4. 압축 요약: 문제 요약과 개념 요약을 프롬프트용으로 짧게 줄인다.

2~4번 초안은 gemma4로 밤새 만들어도 되고 Claude로 한 번에 만들어도 된다. 어느 쪽이든 변이체는 코드 실행으로, 문장은 사람이 한 번 보고 확정한다.

동시에 돌 때와 실패할 때

  • 문제 세션마다 asyncio 작업 하나. 새 이벤트가 오면 진행 중인 ①②를 취소한다. 이미 화면에 흘러나오는 말하기는 끝까지 둔다.
  • Ollama 호출은 줄 하나로 세운다. 내가 직접 누른 요청(힌트, 질문)이 자동 팁보다 먼저다.
  • Ollama가 꺼져 있거나 10초 안에 답이 없으면 분류별 정해진 문장으로 대신한다. ①②는 AI 없이도 돈다.
  • JSON이 깨지면 한 번만 다시 묻고, 또 깨지면 정해진 문장을 쓴다.
  • 단계마다 입력, 출력, 걸린 시간을 남긴다. 코치 평가는 이 기록으로 단계별로 따로 잰다.

실시간 팁 프롬프트 뼈대

[system]
너는 코딩 테스트 연습을 돕는 선배다. 규칙:
- 정답 코드나 고친 코드를 쓰지 않는다. 변수 이름 정도만 말한다.
- 아래 [신호]에 적힌 사실 하나에 대해서만 말한다. 신호에 없는 버그를 지어내지 않는다.
- 먼저 질문 하나를 던진다. 세 문장 안. 쉬운 한국어.
- 확신이 없으면 confidence를 낮게 쓴다.

[문제] {볼트의 문제 요약, 제한}
[신호] {종류, 반례 입력, 기대값, 내 답, 의심 줄}
[열린 힌트 자료] {힌트 단계까지의 풀이 문서 조각}
[내 코드] {줄 번호 붙인 코드}

→ 출력 스키마
{"kind": "question|nudge|warning|praise", "line": int|null,
 "message": string(≤220자), "concept_id": string|null, "confidence": 0~1}

속도는 아직 재지 않았다. 첫 단계에서 이 맥으로 첫 글자까지 걸리는 시간과 초당 토큰 수를 재고, 실시간 팁이 3초 안에 시작하지 않으면 E4B로 내린다.

코치 평가

코치가 쓸 만한지 감으로 정하지 않는다. 기준 풀이 90개에 일부러 버그를 심어 시험지를 만들고, 코치에게 풀게 한다.

  • 심는 버그: 경계 하나 어긋남(±1), <와 <= 바꾸기, 빈 입력·최소 입력 처리 빼기, 효율적인 반복문을 이중 반복문으로 바꾸기, 정렬 기준 뒤집기. 문제당 3개, 모두 270개.
  • 단계별로 따로 잰다: 버그 270개 중 실수 지문과 수리 검색이 AI 없이 잡는 비율을 먼저 잰다. 이 부분은 Ollama 없이도 지금 잴 수 있다. 나머지가 AI 진단으로 가는 몫이다.
  • 재는 것: 팁이 가리킨 줄이 심은 버그 줄과 맞는 비율, 유출 검사 전·후 유출 수, 첫 글자까지 걸린 시간, 확신 값과 실제 적중의 관계.
  • 통과선(제안): 유출 검사 뒤 유출 0건. 줄 적중이 낮으면 줄 번호 없이 질문만 하도록 낮춘다.
  • 쓰면서는 "도움됨 / 별로" 버튼 기록을 같은 표에 쌓는다.

구현 순서

AI 없이도 쓸모 있는 것부터 만든다. 2단계까지만 해도 "반례를 찾아 주는 연습기"가 된다.

단계만드는 것끝났다는 기준
0 · 준비Ollama 설치, 12B·E4B 내려받기, 속도 측정모델 결정과 측정값 기록
1 · 문제 팩색인기, 예시 assert 추출, 무작위 비교를 gen/reference로 옮기기90개 팩 모두 기준 풀이로 통과
2 · 풀기 화면Monaco, 실행기, 예시·숨은 검사, 반례 줄이기, 복잡도 어림버그 심은 풀이에서 반례가 5개 이하 원소로 나온다
3 · 코치신호→개입 규칙→프롬프트→유출 검사, 힌트 사다리, 기록보석 쇼핑 예시가 위 화면처럼 돈다
4 · 코치 평가버그 270개 시험지와 측정 스크립트유출 0건, 지표 기록
5 · 배우기·돌아보기·복습문서 표시, 설명 채점, review-log 연동, 다시 풀기 일정플러그인에서 푼 카드와 기록이 섞여도 어긋나지 않는다
6 · 홈·모의 코테다음 할 일 추천(선수 개념을 다 익힌 개념부터), 모의 코테모의 코테 한 번을 끝까지 치를 수 있다

위험과 대응

위험대응
작은 모델이 없는 버그를 지어낸다테스트로 확인된 신호가 있을 때만 말하게 한다. 확신이 낮으면 칩만 남긴다. 평가 시험지로 적중률을 잰다
답을 흘려 연습이 망가진다정보 차단, 출력 형식 강제, 나중 검사의 세 겹
너무 자주 말해서 흐름이 끊긴다타이핑 중 침묵, 3분 간격, 세 가지 모드
AI에 기대 실력을 착각한다힌트 2단계 이상이면 오답, 모의 코테에서 코치 끔, 간격을 둔 다시 풀기
메모리 16GB가 빠듯하다모델 하나만, KV 캐시 양자화, 문맥 16K, 안 쓰면 30분 뒤 내림
문제 원문 저작권볼트에 정리한 요약 문제문만 보여 주고 원문은 프로그래머스 링크로 연다
시간 초과 판정이 채점 서버와 다르다절대 시간 대신 기준 풀이 시간의 몇 배인지로 판정한다. 「문자열과 알파벳과 쿼리」처럼 기준 풀이도 느린 문제는 따로 표시한다

정할 것

  1. 앱 형태. 로컬 웹앱(추천)과 학습 트레이너 플러그인 확장 중 무엇으로 할까.
  2. 문제 풀이 기록을 review-log.csv에도 남길까. 남기면 홈.md의 오늘 복습 수에 문제가 섞인다. 앱 DB에만 두는 쪽을 추천한다.
  3. 통과한 내 풀이를 볼트에 저장할까. 저장한다면 알고리즘/2.필기노트/가 맞는 자리다. 로드맵에도 링크가 생긴다.
  4. 언어. 처음에는 파이썬만. C++이나 Java가 필요한가.
  5. 문제 늘리기. 90문제 밖(백준 등)도 넣을 계획이 있나. 있으면 문제 팩을 만드는 절차를 일반화해야 한다.
